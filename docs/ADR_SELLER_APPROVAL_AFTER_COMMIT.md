# 판매자 승인과 OPA 전파를 분리한 설계 개선 기록

## 이 기록을 뭐라고 부르면 좋을까

이 문서는 트러블슈팅이라기보다 `설계 개선 기록` 또는 `ADR(Architecture Decision Record, 아키텍처 결정 기록)`에 가깝다.

- 트러블슈팅: 장애 원인 추적과 복구 과정 중심
- 설계 개선 기록 / ADR: 왜 구조를 바꿨는지, 어떤 선택을 했는지, 그 이유와 트레이드오프를 남기는 문서

이번 내용은 "Kafka 장애가 왜 났나"보다 "판매자 승인과 외부 전파를 왜 분리했는가"가 핵심이므로 ADR 성격으로 남기는 편이 맞다.

## 배경

`user-service` 안에는 현재 `auth`와 `seller` 도메인이 함께 존재한다.
서비스는 이미 하나로 합쳐졌지만, 판매자 상태 변경 흐름은 여전히 외부 전파 흐름과 강하게 묶여 있었다.

기존 흐름은 아래와 같았다.

1. 관리자 API가 판매자 승인 요청을 받는다.
2. seller 상태를 변경한다.
3. user 권한을 `SELLER`로 반영한다.
4. OPA hotlist 반영용 Kafka 이벤트를 발행한다.

문제는 2, 3, 4가 사실상 한 덩어리처럼 움직였다는 점이다.

즉 Kafka 전파가 실패하면 판매자 승인 자체도 실패하거나 롤백될 수 있었다.

## 왜 이 구조가 문제였는가

판매자 승인이라는 핵심 비즈니스 작업의 본질은 다음이다.

- seller 상태를 `APPROVED`로 바꾼다.
- 필요하면 user 권한을 `SELLER`로 바꾼다.

반면 OPA hotlist 이벤트 발행은 다음 성격이다.

- 외부 권한 계층에 변경 사실을 전파한다.
- 내부 상태 변경 이후의 후속 작업이다.
- 비동기 전파 또는 eventual consistency를 허용할 수 있는 영역이다.

둘을 한 트랜잭션처럼 취급하면 다음 문제가 생긴다.

- Kafka 브로커가 잠깐 죽어도 승인 자체가 실패한다.
- 외부 시스템 가용성이 내부 도메인 변경을 막는다.
- 로컬 개발 환경에서도 Kafka 미기동이 관리자 승인 API 실패로 이어진다.
- 핵심 비즈니스 작업과 외부 전파 작업의 실패 원인이 분리되지 않는다.

즉 내부 상태 변경과 외부 전파가 너무 강하게 결합되어 있었다.

## 이번 결정

판매자 승인 자체는 먼저 커밋하고, OPA 전파는 커밋 이후에 수행하도록 구조를 바꿨다.

정리하면 다음과 같다.

### 변경 전

1. seller 상태 변경
2. user 권한 변경
3. Kafka 발행
4. 중간에 Kafka 예외가 나면 전체 실패 가능

### 변경 후

1. seller 상태 변경
2. user 권한 변경
3. 트랜잭션 커밋
4. 커밋 이후 OPA hotlist 이벤트 발행
5. 전파 실패는 로그로 남기고 승인 자체는 유지

## 코드에서 어떻게 바뀌었나

핵심 변경점은 [`AuthService.java`](/C:/Users/mm206/devcourse/team02-project/beadv2_2_dogs_BE/baro-user/src/main/java/com/barofarm/user/auth/application/AuthService.java) 에 있다.

- `handleSellerStatusChanged(...)` 에서 OPA hotlist 이벤트를 즉시 발행하지 않음
- `publishSellerStatusEventAfterCommit(...)` 로 커밋 이후 전파
- 전파 실패는 `publishSellerStatusEventSafely(...)` 에서 로그로 남기고 삼킴

즉 "승인"과 "전파"의 실패를 분리했다.

## 이 결정의 장점

### 1. 승인 자체의 안정성이 올라간다

Kafka가 잠깐 불안정해도 판매자 승인 DB 반영은 유지된다.

### 2. 내부 상태 변경과 외부 전파를 분리할 수 있다

seller 도메인의 핵심 상태 변경은 내부 책임으로 두고,
OPA/Gateway 같은 외부 반영은 후속 작업으로 다룰 수 있다.

### 3. 로컬 개발 경험이 좋아진다

Kafka가 완전히 준비되지 않았더라도 승인 기능 자체를 검증할 수 있다.

### 4. 장애 분석이 쉬워진다

이제 "승인 실패"와 "OPA 전파 실패"를 별개의 문제로 볼 수 있다.

## 트레이드오프

이 구조는 일시적 불일치를 허용한다.

예를 들면:

- DB에서는 이미 `APPROVED`
- 하지만 OPA는 아직 예전 상태

즉 짧은 시간 동안은 DB 상태와 외부 권한 상태가 어긋날 수 있다.

하지만 이런 eventual consistency는 외부 전파 영역에서는 일반적으로 허용 가능한 편이다.
오히려 외부 전파 실패 때문에 핵심 비즈니스 트랜잭션이 무너지는 것보다 더 낫다.
